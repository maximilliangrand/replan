# External provider compatibility assessment

Research date: **2026-09-23**. This is a review of public vendor documentation, **not an integration or sandbox validation result**. No account was created, credential used, label purchased, pickup booked, or physical shipment sent.

**No assessed off-the-shelf pair is documented to satisfy Replan's complete current contract.** The most useful first technical investigation is an owned Odoo inventory test instance plus ShipStation API's parcel sandbox, if those products fit the intended operator. That pairing requires a narrower initial workflow and provider-specific lifecycle changes before execution can be enabled. Product selection remains open.

## What must match

The current [provider boundary](../src/providers.ts) and [executor](../src/engine.ts) require more than HTTP endpoints:

- A reservation conditionally changes authoritative inventory, binds the exact payload to a stable action key, and can be retrieved after a lost response.
- `carrier.dispatch` means a committed transfer. Its receipt currently permits inventory consumption and marks the action completed. A purchased shipping label does not establish that physical event.
- Cancellation must settle an in-flight creation race: either report the existing commitment or permanently fence the same key. An absent lookup, cancelled batch status, refund request, or local adapter tombstone alone does not establish that guarantee at a remote provider.
- Recovery can occur after a long outage. Provider deduplication expiry therefore changes what retries are safe.

## Proposed staged approach

This section is an engineering recommendation, not a claim about vendor behavior or completed work.

1. **Validate reads first.** Use the operator's chosen test inventory instance and shipping sandbox to read stock, map company/location/item identities, retrieve rates, and generate proposals with execution disabled. Clearly label this as connected planning, not completed transfer recovery.
2. **Implement inventory operations where their transaction can be authoritative.** For Odoo, a reviewed module would need a unique operation-key record, exact-payload comparison, stock concurrency checks, durable receipts, and terminal cancellation in the same database transaction as the relevant stock reservation/release. A local Replan lock around multiple remote RPCs cannot provide this. A version token must cover competing native inventory changes too; an adapter-only counter is insufficient.
3. **Split the shipping lifecycle.** Model shipment preparation, label purchase, label-purchase uncertainty, label void/refund, physical handoff, and delivery separately. Persist provider IDs before purchasing labels where the provider supports this workflow. Bind approval to the actual service, quote, currency, packages and destinations. Consume source inventory only at the agreed authoritative stock-movement boundary, not merely when a label is returned.
4. **Make unsupported cancellation explicit.** Keep uncertain effects blocked until there is positive provider evidence. Do not map a successful refund submission to Replan's terminal `cancelled` result. If the selected provider cannot offer an equivalent fence, change the workflow and expose the unresolved state rather than claiming the simulator's guarantee survives unchanged.

## Evidence needed before enabling external execution

For the selected account, API version and carrier, retain redacted request/response evidence for duplicate creation, concurrent identical requests, changed payload with a reused key, timeout after acceptance, lookup visibility, process restart, cancellation-versus-creation, and recovery after the deduplication window. Verify inventory reservation behavior alongside native inventory operations and establish when goods physically leave the warehouse. Sandbox passes alone cannot prove undocumented concurrency guarantees or production carrier behavior.

No such vendor tests have been run. The missing inputs are the intended inventory product/version, shipping provider and actual carrier, test-account access, and the operator's definition of committed handoff. These determine the adapter design; they are not interchangeable configuration values.
